# Delivery and engine choice

| Designer's need | Agent implementation | Acceptance check |
| --- | --- | --- |
| One file that travels on a USB drive | Inline scripts, CSS, icons, textures, audio and model bytes. Bundle module imports and embed WASM or use a compatible in-memory loader. Keep simulation independent from packaging. | Copy just the resulting HTML to an otherwise empty directory. Open via file URL in a fresh browser with networking disabled. Start, act, save, reload and act again. |
| Share a link to a solo game | Deploy the built static directory over HTTPS to the intended host. Use paths that work at the deployed base path. Cache immutable assets by content hash. | Open the actual URL from a fresh browser. Check startup, assets, input and a playable action. |
| Human rooms | Serve a shared rendezvous and message service alongside the client. Choose authority for the game before choosing transport. | Follow the two-client checks in multiplayer.md. |
| Both editions | Produce both from the same rules and content. Put network capabilities behind an adapter. The offline menu can point to online rooms. | Compare a representative rule, reward or victory across both builds. Check no extra downloaded assets are needed by solo. |

**Choose the least expensive renderer that can express the core decision.** A card or logistics game can use semantic HTML, keyboard focus and a pure turn reducer. Canvas 2D works well for sprites, grids and immediate feedback. For an explorable low-poly world, Three.js renders and Rapier can handle solid bodies and capsule movement. Blender is an optional authoring tool. Export GLB with agreed metres, up axis, origin, clip names and attachment points. Import the actual file, inspect scale, facing and animations, and test on a selected character. Only add a physics engine when solving physical constraints changes play.

**Source and delivery have different shapes.** Modular development plus a one-file distribution is often easier than writing the source in one HTML. For a small game, native inline code may already satisfy both. For a large game, build modules first, have the single-file pass inline the built entry and asset data, escape closing script tokens, and embed dependency notices. Test with the dev server shut down. Check file-origin storage in the chosen browser and handle unavailable storage gracefully. Define where saves live; moving a file or switching origin can change the storage available. Offer explicit export/import when portable saves are part of the brief.

**Input and budget.** Keep a fixed simulation step independent of rendering; clamp catch-up after tab suspension. Map player actions semantically across keyboard, pointer and touch. Put core actions within reach, clear held keys on blur, separate click from drag, and handle pointer-lock denial. Avoid requiring browser-reserved gestures. Stream terrain around the player, use instancing or shared materials, bake distant detail and cap particles. Measure frame time in a demanding scene at the actual low preset. Record resource size, viewport, devices tested and any untested hardware.

**Operating the project.** Run the project's normal development, test and production commands. Verify an existing deployment's ownership and intended audience before publishing within the user's authorization. For a new remote host, the user may need to provide a hosting target. Deliver the verified local build while that dependency is pending. Never embed private service credentials in a downloadable client.
