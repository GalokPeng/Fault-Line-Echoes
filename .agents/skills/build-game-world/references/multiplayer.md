# Implementing remote play

Ask which *human interaction* matters: simultaneous duelling, shared work on one object, asynchronous turns, or simply seeing another visitor. Decide what is shared (turn, clock, score, object, contested loot) and what stays private (solo journal, cosmetic collection). The designer chooses fairness and stakes. The agent owns protocol and transport.

**A reachable session.** Give the lobby a real create/join flow, room ID or invite URL, join deadline, capacity limit, departure state and actionable connection feedback. For a small turn-based game an HTTPS service with ordered turns may suffice. For fast shared simulation choose an authoritative host for friendly play or a dedicated server for distrusting clients. A serverless process's in-memory map is useful locally; use a suitable shared store or stateful room in production.

**Messages and authority.** Specify a session/round identity, protocol version and actor identity. Keep discrete commands ordered and deduplicated with sequence IDs; a fresh position snapshot can replace an older one. Validate known actions, turn ownership, cooldown, range and line of sight at the authority. Clients render predicted feedback and reconcile the accepted result. For an authoritative turn game, use a turn/version precondition so two taps cannot consume the same turn. Sync role, skin, pose and skill IDs; only a confirmed impact triggers shared hit feedback. Restore equal baseline stats at round start if the brief calls for a fair arena.

**A room code is discovery, not delivery.** WebRTC needs signalling and a viable ICE route. Private networks may prevent a direct route even when pairing succeeds. Provide a reachable relay, for example an authenticated and scoped HTTPS/WebSocket game relay or a configured TURN service. A transport switch needs replay/deduplication, stale-update suppression and a clear terminal state. Compare cadence to the genre's latency budget. Bound room lifetime, queue size and payload size; scope access to the paired clients. Publish only endpoints and public client configuration in HTML.

**Prove it.** Start two independent browser contexts with separate storage, join by code, take different roles and perform an action that changes the other's screen and the score or shared objective. Check a failed join and what both players see on disconnect. When fallback is promised, force direct connectivity off, repeat that action over relay, then interrupt an established direct path. Verify retries cannot double-award. If possible try two physical networks; say which conditions were simulated. Local tabs exchanging BroadcastChannel messages demonstrate same-origin local communication only. Leave the verified solo path accessible when a room service is unavailable.
